# RCSS Arena — مخزن عمومی + Render رایگان

شرح اجزای احراز هویت و مسیر توکن‌ها: [AUTHENTICATION.md](AUTHENTICATION.md).

این بسته برای مخزن عمومی https://github.com/tahalkhaftan/RCSS-arena آماده شده است. سایت روی Render Free اجرا می‌شود و مسابقه‌ها با RCSSServer 19.0.0 روی GitHub Actions انجام می‌شوند. سورس رسمی سرور در پوشهٔ vendor قرار دارد و Workflow آن را روی runner می‌سازد؛ فایل باینری نصب‌شده و وابسته به سیستم خاصی در مخزن نیست.

## عمومی‌بودن چه معنایی دارد؟

کد سایت، ابزار اجرا و Workflow در مخزن عمومی قابل‌دیدن و کپی‌کردن هستند. عمومی‌بودن مخزن و مخفی‌بودن همان کد با هم ممکن نیست. برای رزومه، این پروژه را عمومی می‌گذاریم و کد/باینری تیم‌های فوتبال را داخل آن قرار نمی‌دهیم.

فایل‌های آپلودی و نتایج در مخزن خصوصی جداگانه ذخیره می‌شوند. برنامه قبل از دسترسی به داده‌ها خصوصی‌بودن آن مخزن را بررسی می‌کند و مخزن عمومی را رد می‌کند. دسترسی مدیر سایت و کسانی که به مخزن خصوصی دسترسی دارند برقرار است؛ این حفاظت، رمزنگاری سرتاسری نیست.

## نصب قدم‌به‌قدم

۱. فایل ZIP را استخراج کن. تمام محتویات پوشهٔ rcss-arena-public، شامل پوشهٔ مخفی .github، باید در ریشهٔ مخزن عمومی RCSS-arena روی شاخهٔ main باشد. فقط خود ZIP را آپلود نکن. اطلاعات تیم‌ها و رمزها را داخل این مخزن نگذار.

۲. یک مخزن دیگر با نام RCSS-arena-data بساز، حتماً Private، و هنگام ساخت Add README را فعال کن. این مخزن فقط محل نگهداری ZIP تیم‌ها، config.json، results.json و logs.zip است. هیچ Workflow مسابقه‌ای در آن قرار نمی‌گیرد. خصوصی‌بودن این مخزن را تغییر نده.

۳. یک Fine-grained personal access token مخصوص مخزن خصوصی بساز:
- Repository access: فقط RCSS-arena-data
- Contents: Read and write
- تاریخ انقضا تعیین کن.
در مخزن عمومی: Settings → Secrets and variables → Actions
- در Secrets، STORAGE_TOKEN = همین توکن
- در Variables، STORAGE_REPOSITORY = tahalkhaftan/RCSS-arena-data
توکن را در چت یا فایل منتشرشده نگذار.

۴. یک توکن جدا برای Render بساز، با دسترسی محدود به هر دو مخزن عمومی و خصوصی و Repository permissions شامل Contents=Read and write و Actions=Read and write. این توکن فقط به سرویس Render داده می‌شود. رمز GitHub لازم نیست.

۵. در Render مخزن عمومی را انتخاب کن:
New → Web Service → Docker → Instance type: Free
دیسک، Worker یا سرویس پولی نساز. فایل render.yaml هم تنظیمات پایه را دارد.

۶. Environment سرویس Render:
- ARENA_USER: نام ورود دلخواه به سایت
- ARENA_PASSWORD: رمز مستقل و طولانی سایت
- GITHUB_REPOSITORY: tahalkhaftan/RCSS-arena
- STORAGE_REPOSITORY: tahalkhaftan/RCSS-arena-data
- GITHUB_TOKEN: توکن جداگانهٔ Render در مرحلهٔ ۴
- GITHUB_REF: main

۷. Deploy کن. سایت را با HTTPS باز کن و نام و رمز سایت را وارد کن. دو ZIP از باینری Linux x86_64 تیم‌ها انتخاب کن و ابتدا یک بازی معمولی اجرا کن. بعد از شروع درخواست می‌توانی صفحه را ببندی؛ مسابقه روی GitHub ادامه دارد. برای نتیجه از «بازیابی آخرین تست» استفاده کن.

Workflow با نام RCSS Matches در Actions ظاهر می‌شود. release_id را سایت می‌سازد؛ فعلاً فرم دستی انتخاب حریف داخل Actions وجود ندارد و تنظیمات بازی از سایت وارد می‌شوند.

## سایر افراد چگونه استفاده می‌کنند؟

هر نفر پروژهٔ عمومی را Fork می‌کند، مخزن خصوصی دادهٔ خودش و سرویس Render خودش را می‌سازد، سپس نام مخزن‌ها و Secretهای خودش را تنظیم می‌کند. همه می‌توانند کد را ببینند و نسخهٔ مستقل راه بیندازند. این نسخه یک سایت مشترک با ثبت‌نام آزاد برای اجرای باینری ناشناس نیست. رمز سایت خودت را عمومی منتشر نکن.

## رابط و فرایند

Left و Right: فایل ZIP، نام تیم، پوشهٔ نسبی، دستور شروع.
تعداد دورها × تعداد بازی هر دور: تعداد کل بازی‌ها.
حالت: معمولی یا synch_mode، بسته به پشتیبانی تیم‌ها.
پس از هر بازی: نتیجه در JSON ذخیره می‌شود؛ بالای JSON خلاصهٔ برد، مساوی، باخت، گل و میانگین مالکیت نمایش داده می‌شود. پایان درخواست: ZIP شامل JSON و .rcg/.rcl و خروجی تیم‌ها و سرور قابل‌دانلود می‌شود.

مثال پوشه: AITech-2D/bin/
مثال دستور: ./start.sh -h {host} -p {port}
یا: ./localStartAll
دستور باید تمام ۱۱ بازیکن را اجرا کند. placeholderها: {host}، {port}، {coach_port}، {olcoach_port}. آرگومان‌ها باید مطابق اسکریپت واقعی تیم باشند. فعلاً فقط باینری ZIP پذیرفته می‌شود؛ Build سورس تیم در فرم پیاده نشده است.

مالکیت برآورد محدودهٔ قابل‌ضربهٔ بازیکنان در play_on است و چهار دستهٔ چپ، راست، آزاد و مشترک دارد. میانگین سادهٔ درصد بازی‌های کامل‌شده نمایش داده می‌شود. این عدد تعریف تحلیلی برنامه است و آمار رسمی مالکیت RCSS نیست؛ روش داخل JSON ذکر می‌شود.

## سهمیه و کیفیت

Runner استاندارد Ubuntu x64 مخزن عمومی طبق مستندات فعلی ۴ CPU، ۱۶GB RAM و ۱۴GB SSD دارد. اجرای استاندارد مخزن عمومی رایگان است، با محدودیت‌های سرویس و قوانین استفاده؛ به معنی VPS دائمی یا اجرای نامحدود بدون هیچ محدودیتی نیست. از Larger runner پولی استفاده نکن.

Render Free بعد از ۱۵ دقیقه بی‌ترافیک می‌خوابد و دیسک آن موقت است؛ چون مسابقه روی GitHub اجرا می‌شود و فایل‌ها در مخزن خصوصی هستند، خواب سایت نباید آن‌ها را از بین ببرد. پلن رایگان محدودیت ساعات، انتقال داده و Build دارد. بدون روش پرداخت، عبور از سهمیه معمولاً باعث توقف سرویس می‌شود. این برنامه تنظیمات Billing حساب را کنترل نمی‌کند.

- مجموع دو ZIP حداکثر ۳۲ MiB، هر درخواست حداکثر ۵۰ بازی.
- بازی‌ها ترتیبی، نه هم‌زمان؛ یک درخواست فعال برای هر سایت.
- Workflow تا ۱۵۰ دقیقه و هر بازی تا ۳۰ دقیقه. تعداد زیاد ممکن است از سقف Workflow عبور کند.
- توقف کنترل‌شده حدود ۳۰ ثانیه برای تشخیص نیاز دارد. Cancel workflow فوری ممکن است ZIP پایانی تولید نکند.
- نسخه برای تیم‌های مورد اعتماد است؛ جداسازی امنیتی مخصوص کد ناشناس ندارد. حذف توکن از محیط بازیکنان جای Sandbox واقعی را نمی‌گیرد.
- فایل‌های قدیمی را پس از دانلود از مخزن خصوصی حذف کن؛ ذخیره‌سازی بی‌نهایت فرض نشده است.
- CPU/RAM واقعی موردنیاز باید با تیم خودت و حریف اندازه‌گیری شود. GPU و مانیتور گرافیکی برای اجرای خود مسابقه لازم نیست.

## وضعیت آزمون

آزمون‌های محلی شامل لاگ مصنوعی، سرور UDP ساختگی، اعتبارسنجی ZIP و API گیت‌هاب ساختگی هستند. اجرای واقعی روی Render/GitHub و مسابقه با باینری تیم‌های تو هنوز تأیید نشده‌اند. تنظیمات درست و آزمون یک بازی واقعی آخرین مرحلهٔ راه‌اندازی است.

برای اجرای بررسی‌ها: python3 -m unittest discover -s tests -v
فایل README.md معرفی انگلیسی پروژه برای صفحهٔ GitHub است. LICENSE فقط کد جدید Arena را پوشش می‌دهد؛ مجوز سورس upstream و مشخصات commit آن در THIRD_PARTY.md آمده است.

### پخش مستقیم مانیتور

برای تست‌های جدید، سایت اطلاعات اتصال زنده و یک مجوز محدود به همان تست را
در `live.json` مخزن خصوصی ذخیره می‌کند. Runner حداکثر ۱۰ فریم در ثانیه نمونه‌برداری
می‌کند و در یک رشتهٔ جدا، بسته‌ها را مستقیماً به Render می‌فرستد. مرورگر با SSE
فریم‌ها را دریافت می‌کند؛ مسیر نمایش زنده به API گیت‌هاب وابسته نیست.

بعد از انتشار این نسخه روی Render، تست جدید بسازید. تست‌های قبلی و قطع ارتباط
به گزارش دوره‌ای برمی‌گردند. در رابط، «پخش مستقیم» و «گزارش دوره‌ای» مشخص می‌شوند.
تأخیر اینترنت و Render تضمین‌شده نیست؛ در حالت سریع، نمایش نیز از زمان واقعی
مسابقه سریع‌تر پیش می‌رود. بازپخش همچنان از RCG کامل خوانده می‌شود.

آدرس سرویس از `RENDER_EXTERNAL_URL` دریافت می‌شود؛ در میزبانی دیگر می‌توان
`ARENA_PUBLIC_URL` را با یک URL معتبر HTTPS تنظیم کرد. این پیاده‌سازی برای یک
نمونهٔ سرویس Render است؛ چند نمونه به یک واسطهٔ مشترک پیام نیاز خواهند داشت.
مجوز پخش ۲۴ ساعت اعتبار دارد و در گزارش‌ها، ZIP خروجی و محیط پردازش تیم‌ها قرار
نمی‌گیرد. تغییر رمز سایت، مجوزهای قبلی را باطل می‌کند.


### نمرهٔ نمایشی تیم‌ها

نمرهٔ ۰ تا ۱۰ یک شاخص ابتکاری Arena است، نه xG یا رتبه‌بندی رسمی.
برای بازپخش، کل فریم‌های فایل تحلیل می‌شوند؛ نمرهٔ زنده فقط فریم‌های دریافت‌شده را
پوشش می‌دهد و پس از قطع ارتباط ممکن است ناقص باشد. کمتر از ۳۰ فریم فعال یا ۱۰
واحد کنترل تخمینی، نمره‌ای نمایش داده نمی‌شود.

کنترل تخمینی: نزدیک‌ترین بازیکن در شعاع ۱٫۳ متر، با حداقل ۰٫۱۵ متر برتری نسبت
به تیم دیگر. خطر: فاصله و زاویهٔ دهانهٔ دروازه و سدکردن مسیر مستقیم توسط مدافع‌ها.
جهت حمله از محل دروازه‌بان و در نبود آن از سمت تیم فرض می‌شود. زمان‌های توقف و
سایکل‌های تکراری در اندازه‌گیری وارد نمی‌شوند؛ وزن فاصلهٔ نمونه‌ها حداکثر ۱۰ سایکل است.

نمرهٔ چپ = ۵ + ۱٫۵ × اختلاف سهم کنترل + ۲٫۵ × اختلاف خطر نرمال‌شده
+ ۰٫۷ × اختلاف کیفیت حرکت و پاس + tanh(اختلاف گل / ۳)، محدود به بازهٔ ۰ تا ۱۰. نمرهٔ راست با علامت معکوس محاسبه می‌شود.
مخرج خطر، مجموع خطر دو تیم به اضافهٔ ۰٫۰۵ × زمان مشاهده‌شده است.
این وزن‌ها انتخاب طراحی Arena هستند و با دادهٔ مسابقات آموزش داده نشده‌اند.
ایدهٔ معیارهای مکانی از توضیح [StatsBomb دربارهٔ کیفیت موقعیت](https://www.hudl.com/blog/upgrading-expected-goals)
گرفته شده؛ شمارش شوت و احتمال واقعی گل در این شاخص محاسبه نمی‌شود.

پاس موفق از جابه‌جایی کنترل توپ بین دو هم‌تیمی و دریبل از پیشروی همان کنترل‌کننده تخمین زده می‌شود.
پاس رو به عمق با عبور از مدافع‌ها وزن بیشتری از پاس جانبی و رو به عقب دارد؛ پیشروی با توپ نیز امتیاز دارد.
این‌ها استنباط از موقعیت‌ها هستند، نه شمارش قطعی فرمان‌ها یا رویدادهای تاکتیکی.
با فاصلهٔ بیش از ۵ سایکل میان نمونه‌ها، پیگیری حرکت بازنشانی می‌شود تا رویداد حدسی ساخته نشود.

### عملکرد بازی انتخاب‌شده

جدول مقایسه‌ای شامل گل، کنترل تخمینی توپ، شوت‌های مشاهده‌شده، پاس و دقت پاس، کرنر و آفساید است.
چیدمان و معیارهای اصلی با الهام از نمونهٔ آمار ورزش سه انتخاب شده‌اند:
https://www.varzesh3.com/news/1764174
جزئیات پاس عمقی و دریبل در بخش بازشدنی باقی هستند. علامت ≈ یعنی برآورد؛ — یعنی دادهٔ کافی نداریم.

گل از score واقعی و کرنر/آفساید از تغییر playmode خوانده می‌شوند؛ تکرار یک حالت در چند فریم دوباره شمرده نمی‌شود.
مرجع پروتکل و stateها: https://rcsoccersim.readthedocs.io/en/latest/soccermonitor.html
شوت صرفاً با جهت حرکت توپ ثبت نمی‌شود: ابتدا افزایش شمارندهٔ ضربه یا state ضربهٔ موفق، سرعت توپ و مسیر رو به دروازه در ۳۵ متر پایانی بررسی می‌شوند.
سپس یک پایان قابل مشاهده لازم است: عبور از خط دروازه، افزایش امتیاز، catch موفق دروازه‌بان حریف یا قطع مسیر توسط حریف.
دریافت توپ توسط هم‌تیمی، پاس است و به عنوان شوت شمارش نمی‌شود.
مهار فقط با catch موفق دروازه‌بان در مسیر ضربهٔ نامزد ثبت می‌شود؛ از تفاضل شوت و گل محاسبه نمی‌شود.
کل شوت‌های تشخیص‌داده‌شده برابر مجموع در چارچوب، خارج چارچوب و مسدودشده است.
این تشخیص‌ها محافظه‌کارانه و همچنان ابتکاری هستند؛ قصد تاکتیکی بازیکن مستقیماً در RCG ثبت نمی‌شود.
نبود metadata ضربه/سرعت، آمار شوت و مهار را ناموجود می‌کند؛ فاصلهٔ بیش از ۵ سایکل پیگیری اقدام را قطع می‌کند.

پاس از انتقال کنترل به بازیکن دیگر پس از حداقل ۳ متر تخمین زده می‌شود؛ رسیدن به حریف یا خروج معتبر توپ ناموفق است.
پاس عمقی در این شاخص حداقل ۸ متر پیشروی در جهت حمله دارد. دقت پاس از پاس‌های با پایان تشخیص‌داده‌شده محاسبه می‌شود، نه تمام فرمان‌های kick.
کنترل توپ درصد زمان‌های کنترل قابل تشخیص دو تیم است و زمان توپ آزاد از مخرج خارج می‌شود.
دریبل موفق از ۴ متر پیشروی با همان کنترل‌کننده و ناموفق از از دست دادن کنترل در نزدیکی او پس از حرکت تخمین زده می‌شود.
آمار با لحظهٔ مانیتور هماهنگ است؛ عقب‌رفتن بازپخش آمار آینده را نمایش نمی‌دهد.
پخش زنده فقط نمونه‌های دریافت‌شده را پوشش می‌دهد؛ برای پوشش بهتر، RCG کامل را بخوانید.
داده‌های مانیتور در JSON نتایج ذخیره نمی‌شوند.

### ذخیرهٔ عملکرد هر مسابقه در JSON

هر عضو `matches` اکنون یک `performance` مستقل دارد: `left` و `right` شامل گل، درصد کنترل توپ، پاس‌ها و دقت پاس، شوت‌های تشخیص‌داده‌شده، مهار، کرنر، آفساید و دریبل هستند.
تحلیل نهایی بعد از هر بازی، از RCG کامل انجام می‌شود و همراه همان نتیجه، ZIP و فایل results.json منتشر می‌شود. نتایج قبلی خودکار بازنویسی نمی‌شوند.
برای جلوگیری از تفاوت دو پیاده‌سازی، کارگر Python با Node.js همان طبقه‌بند خالص مانیتور را اجرا می‌کند؛ Node.js در وابستگی‌های Workflow نصب می‌شود. Render فقط کنترل‌پنل را اجرا می‌کند و این تحلیل در Actions انجام می‌شود.
شعاع کنترل هر بازیکن از server_param و player_type خوانده می‌شود؛ در دادهٔ قدیمی بدون این پارامترها، مقدار پایهٔ ۱٫۰۸۵ متر استفاده می‌شود.
`quality` تعداد فریم‌های فعال، سایکل‌های مفقود، بازنشانی پیگیری، پوشش metadata ضربه و گل‌های بدون شوت تشخیص‌داده‌شده را گزارش می‌کند.
`status: complete` فقط پوشش لاگ از شروع تا پایان طبیعی را مشخص می‌کند، نه بی‌خطابودن تشخیص تاکتیکی.
گل، کرنر و آفساید از state/score ثبت‌شده می‌آیند؛ بقیهٔ معیارها همچنان استنباطی و با فهرست `estimated_metrics` مشخص‌اند. دادهٔ ناموجود null است؛ رویداد حل‌نشده به پاس یا شوت ساختگی تبدیل نمی‌شود.
آمار unavailable همراه علت، در صورت نبود لاگ یا خطای تحلیل، نگه داشته می‌شود و نتیجهٔ خود مسابقه را تغییر نمی‌دهد.
در مانیتور زنده، آمار نهایی بازی انتخاب‌شده پس از پایان از همین نتیجهٔ ذخیره‌شده نمایش داده می‌شود. هنگام مرور گذشته، آمار همان لحظه باقی می‌ماند.
فایل RCG محلی نیز گزارش performance دارد، اما همچنان در مرورگر خوانده می‌شود. هیچ فریم یا مختصاتی در performance ذخیره نمی‌شود.

حرکت با توپ موفق در رابط با علامت ٪ نمایش داده می‌شود: موفق / (موفق + ناموفق) × ۱۰۰، بر اساس رخدادهای تشخیص‌داده‌شده. نبود رخدادِ قابل محاسبه به صورت — و null باقی می‌ماند.
در performance هر تیم، ball_carries شامل successful، failed و success_rate_percent است؛ dribbles برای سازگاری گزارش‌های قبلی حفظ شده است.


## آپلود سورس و بیلد تیم

کنار عنوان هر تیم، فلش حالت ورودی را باز کنید و «آپلود سورس و بیلد» را انتخاب کنید. فایل ZIP کل پروژه را بدهید، بیس دانش‌آموزی یا دانشجویی را انتخاب کنید و دستور شروع دلخواه را وارد کنید. پوشه سورس اختیاری است: پوشه اصلی دارای `bootstrap` خودکار پیدا می‌شود؛ اگر چند پروژه هم‌سطح وجود دارد، مسیر نسبی پروژه را وارد کنید.

هر تیم سورس، یک بار پیش از مسابقه‌ها روی GitHub Actions بیلد می‌شود. ابتدا در ریشه پروژه `./bootstrap` و سپس `./configure` اجرا می‌شوند:
- دانش‌آموزی: `mkdir -p build`، سپس در `build`: `cmake ..` و `make -j 8`. پوشه اجرای تیم `build/bin` است.
- دانشجویی: در ریشه `make -j 8`. پوشه اجرای تیم `src` است.

دستور شروع پیش‌فرض `./start.sh` است و می‌توان آن را عوض کرد. حالت «آپلود باینری» همچنان مسیر و دستور شروع قبلی را می‌پذیرد.

اگر بیلد شکست بخورد، مسابقه شروع نمی‌شود و بخش بازشدنی «ارور» خروجی کامل ترمینال همان تیم را نمایش می‌دهد. خروجی در فایل `build-left.log` یا `build-right.log` در مخزن ذخیره‌سازی خصوصی و داخل ZIP لاگ‌ها نیز نگه‌داری می‌شود. ابزارهای عمومی بیلد نصب هستند؛ وابستگی اختصاصی هر تیم باید جداگانه فراهم باشد. بیلد روی Render اجرا نمی‌شود.
